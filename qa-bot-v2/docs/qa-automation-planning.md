# QA 자동화 기획 및 설계 문서

작성일: 2026-07-24  
대상 프로젝트: `qa-bot-v2`  
대상 서비스: LiveAnywhere Android 앱 Dev/Staging 환경

---

## 1. 문서 목적

이 문서는 LiveAnywhere Android 앱 QA 자동화의 목적, 운영 방식, 지원 명령어, 현재 구현된 시나리오, PASS/FAIL 기준, 향후 확장 방향을 정리한다.

Notion에 업로드하여 QA, 개발, PM, 운영 담당자가 같은 기준으로 자동화 범위와 진행 상태를 확인할 수 있도록 한다.

---

## 2. 자동화 목적

반복적으로 수행되는 모바일 앱 QA 시나리오를 Slack 명령어로 실행하고, 실행 결과를 구조화된 리포트로 남겨 QA 속도와 재현성을 높인다.

핵심 기대 효과:

- QA 담당자가 매번 단말을 수동 조작하지 않아도 주요 시나리오를 빠르게 확인할 수 있다.
- Slack에서 명령어를 입력하면 연결된 QA 단말에서 자동으로 테스트가 실행된다.
- 각 실행마다 `run_id`가 발급되어 결과 추적이 가능하다.
- 실패 시 스크린샷, UI dump XML, runner log를 남겨 실패 원인을 빠르게 확인할 수 있다.
- 게스트/호스트 역할별 핵심 E2E 플로우를 표준화할 수 있다.
- 개발자가 Dev 앱에서 빠르게 확인해야 하는 이슈와 QA가 Staging 앱에서 확인해야 하는 회귀 테스트를 같은 구조로 실행할 수 있다.

---

## 3. 자동화 기본 원칙

### 3.1 기존 운영 봇과 분리

기존 `issue-bot.js`는 사용하지 않고 새 프로젝트 `qa-bot-v2`에서 자동화를 진행한다.

분리 목적:

- 기존 운영 봇 안정성 유지
- 테스트 실행, 리포트, Slack 응답 구조 분리
- 기능 단위로 안전하게 확장

### 3.2 Slack은 실행 인터페이스

Slack Bot은 테스트 로직을 직접 들고 있는 주체가 아니라, 테스트 실행을 요청하고 결과를 전달하는 ChatOps 인터페이스 역할을 한다.

```text
Slack 명령어
-> qa-bot-v2
-> command-router
-> test orchestrator
-> test runner
-> Android 단말 조작
-> reports/{run_id} 저장
-> Slack 결과 응답
```

### 3.3 앱 재실행 기준

개발 완료 후 테스트하는 핵심 케이스는 앱을 완전히 종료한 뒤 재실행해서 시작한다.

적용 대상:

- 로그인
- 검색
- 계약 요청
- 계약 결제
- 계약 취소

로그아웃은 로그인 상태 여부에 따라 내 정보 화면 진입 후 진행한다.

### 3.4 스크린샷 저장 기준

스크린샷은 원칙적으로 실패 상황 중심으로 저장한다.

목적:

- 성공 케이스 실행 속도 개선
- 리포트 용량 절감
- 실패 화면 중심의 원인 분석 강화

### 3.5 PASS 판정 기준을 엄격하게 유지

자동화가 버튼을 눌렀다는 사실만으로 PASS 처리하지 않는다.

PASS는 다음 상태를 실제 화면/XML로 확인해야 한다.

- 로그인 후 홈 화면 또는 역할별 최종 화면 확인
- 검색 결과 목록 화면 확인
- 계약 요청 완료 화면 및 홈 복귀 확인
- 결제 완료 화면 및 홈 복귀 확인
- 계약 취소 완료 화면 및 홈 복귀 확인

## 4. 실행 환경

### 4.1 대상 앱

```text
dev: com.live1month.live1month.dev
staging: com.live1month.live1month.staging
```

Slack 명령어 뒤에 `dev` 또는 `stg`를 붙여 실행 환경을 선택한다. 생략하면 `stg`로 실행한다.

### 4.2 단말 역할

```text
guest: ADB_GUEST_DEVICE
host: ADB_HOST_DEVICE
```

두 역할은 `.env`에서 관리한다.

```env
ADB_GUEST_DEVICE=R3CT80QJ3NL
ADB_HOST_DEVICE=R3CR30K439K
```

### 4.3 Slack Bot 실행

```bash
cd "/Users/liveanywhere_test/Documents/자동화 프로젝트/qa-bot-v2"
caffeinate -i /opt/homebrew/bin/node src/app.js
```

## 7. 주요 시나리오 기준

### 7.0 기본검증 1사이클

기본검증은 개별 테스트를 묶어 주요 계약 플로우를 한 번에 확인하는 스모크 테스트다.

일반결제:

```text
게스트 로그인
-> 정확한 일정 검색/집 상세 진입/계약 요청
-> 호스트 로그인 상태 확인 또는 자동 로그인
-> 호스트 계약 승인
-> 게스트 로그인 상태 확인 또는 자동 로그인
-> 게스트 일반카드 결제
```

무통장 결제:

```text
게스트 로그인
-> 정확한 일정 검색/집 상세 진입/계약 요청
-> 호스트 로그인 상태 확인 또는 자동 로그인
-> 호스트 계약 승인
-> 게스트 로그인 상태 확인 또는 자동 로그인
-> 게스트 무통장 결제
-> Toss 테스트 결제내역 입금 승인
```

자동결제:

```text
게스트 로그인
-> 정확한 일정 검색/집 상세 진입
-> 계약 요청 화면에서 호스트 수락 즉시 자동 결제 선택
-> 호스트 로그인 상태 확인 또는 자동 로그인
-> 호스트 계약 승인
```

운영 기준:

- 기본검증 내부에서는 계약 요청의 자동 승인 연결을 사용하지 않고, 계약 요청과 호스트 승인을 명시적으로 한 번씩만 실행한다.
- 중간 단계가 FAIL이면 이후 단계는 실행하지 않는다.
- 계약 요청/승인/결제/취소 계열은 필요한 role의 로그인 상태를 먼저 확인하고, 세션이 풀려 있으면 자동 로그인 후 이어서 진행한다.

### 7.1 게스트 로그인

흐름:

```text
앱 완전 종료
-> 앱 재실행
-> 이메일/휴대폰 번호로 시작하기
-> 이메일 입력
-> 비밀번호 입력
-> 로그인
-> 홈 화면 확인
```

PASS 기준:

- 로그인 화면 오류 문구가 없어야 한다.
- 로그인 후 홈 화면 검색바 또는 홈 화면 주요 UI가 보여야 한다.
- 이미 로그인된 상태면 로그인 완료 상태로 인정할 수 있다.

### 7.2 호스트 로그인

흐름:

```text
앱 실행
-> 필요 시 호스트 계정 로그인
-> 호스트모드 진입
-> 하단 계약 탭 진입
```

PASS 기준:

- 호스트모드로 전환되어야 한다.
- 호스트 하단 계약 탭까지 진입해야 한다.

### 7.3 로그아웃

흐름:

```text
내 정보 화면 진입
-> 로그아웃 버튼이 보일 때까지 스크롤
-> 로그아웃 버튼 선택
-> 로그아웃 확인 팝업에서 로그아웃 선택
-> 로그인 시작 화면 또는 로그아웃 상태 확인
```

PASS 기준:

- 로그인된 상태면 실제 로그아웃 완료 상태가 보여야 한다.
- 이미 로그아웃된 상태면 로그아웃 버튼이 없어도 정상 상태로 판단할 수 있다.

### 7.4 정확한 일정 검색

조건:

```text
지역: 국내
일정: 정확한 일정
체크인: 2026-08-01
체크아웃: 2026-08-07
어린이: 1명
유아: 1명
반려동물: 1마리
```

PASS 기준:

- 검색 결과 목록 화면으로 진입해야 한다.
- 지도 일시 오류는 부가 이슈로 기록할 수 있으나, 목록 검색이 가능하면 검색 자체는 PASS로 볼 수 있다.

### 7.5 유연한 일정 검색

조건:

```text
지역: 국내
일정: 유연한 일정
머무는 기간: 일주일
예상 입주월: 7월, 8월
인원: 기본값
```

PASS 기준:

- 검색 결과 목록 화면으로 진입해야 한다.

### 7.6 게스트 계약 요청

흐름:

```text
앱 재실행
-> 정확한 일정 검색
-> 검색 결과 리스트 끌어올리기
-> 검색 결과 첫 번째 숙소 선택
-> 숙소 상세 화면 진입
-> 계약 조건 확인
-> 계약 요청 화면 하단 이동
-> 필수 약관 전체 동의
-> 계약 요청하기
-> 계약 요청 완료 화면 확인
-> 홈으로 이동
```

계약 요청용 검색 조건:

```text
성인: 1명
어린이: 0명
유아: 0명
반려동물: 0마리
```

참고:

- 계약 기간 확인 팝업이 나오는 경우 `요청 계속하기`를 선택한다.
- 팝업이 나오지 않는 경우도 정상 흐름이다.

### 7.7 자동카드 계약 요청

흐름:

```text
계약 요청 화면 진입
-> 결제 수단 영역으로 이동
-> 호스트 수락 즉시 자동 결제 선택
-> 필수 약관 전체 동의
-> 계약 요청하기
-> 계약 요청 완료 화면 확인
-> 홈으로 이동
-> 홈 화면 풀 리프레시
```

PASS 기준:

- 자동카드 결제 수단이 실제로 선택되어야 한다.
- 계약 요청 완료 후 홈 화면으로 복귀해야 한다.

### 7.8 호스트 계약 승인

흐름:

```text
호스트 로그인 또는 기존 호스트모드 확인
-> 계약 탭 진입
-> 계약 요청 건 확인
-> 계약 상세 진입
-> 계약 수락 버튼 선택
-> 계약 수락 팝업에서 수락
-> 수락했습니다 팝업에서 확인
```

PASS 기준:

- 계약 요청이 수락되어야 한다.
- 게스트 결제 가능 상태로 이어질 수 있어야 한다.

### 7.9 호스트 계약 요청 거절

흐름:

```text
호스트 로그인 또는 기존 호스트모드 확인
-> 계약 탭 진입
-> 최신 게스트 계약 요청 결과의 홈 카드 기준 확인
-> 호스트 계약 목록에서 같은 숙소명/일정의 계약 요청 카드 선택
-> 계약 요청 상세 진입
-> 하단 거절 버튼 선택
-> 게스트에게 계약 요청 거절 사유를 알려주세요 화면 진입
-> 드롭박스 선택
-> 기타 제외 4개 항목 중 랜덤 선택
-> 하단 거절 버튼 선택
-> 거절 완료 상태 확인
```

PASS 기준:

- 게스트 홈 카드의 숙소명/일정과 호스트 계약 탭의 숙소명/일정이 일치하는 요청 건을 우선 선택한다.
- 저장된 카드 기준이 없으면 호스트 계약 탭에서 최신 계약 요청 건을 선택한다.
- 거절 사유는 기타를 제외한 항목 중 하나를 선택해야 한다.
- 거절 완료 상태 또는 호스트 계약 목록 복귀 상태가 확인되어야 한다.

### 7.10 일반카드 계약 결제

흐름:

```text
앱 재실행
-> 홈 화면 풀 리프레시
-> 결제 대기 중 카드 선택
-> 계약 상세 진입
-> 확인 및 결제
-> 결제하기 영역에서 신용/체크카드 확인
-> 결제 방법 영역에서 카드 더보기
-> JCB 카드 선택
-> 결제하기
-> PG 화면 카드번호 입력
-> 만료일 입력
-> Required 동의
-> NEXT
-> 결제 완료 화면
-> 홈으로 가기
```

테스트 카드:

```text
카드번호: 3530 1113 3330 0000
만료일: 0328
```

### 7.11 무통장 계약 결제

흐름:

```text
앱 재실행
-> 홈 화면 풀 리프레시
-> 결제 대기 중 카드 선택
-> 계약 상세 진입
-> 확인 및 결제
-> 결제하기 영역에서 무통장 입금 선택
-> 현금영수증 개인 선택
-> 휴대폰 번호 입력
-> 발급 요청
-> 환불/보증금 반환 은행 선택
-> 기업은행 선택
-> 계좌번호 입력
-> 예금주 확인
-> 홍길동님 계좌가 맞나요? 팝업 확인
-> 저장 버튼 선택
-> 결제하기
-> 결제 완료 화면
-> 홈으로 가기
-> 기본검증 또는 연결 실행에서는 Toss 테스트 결제내역 입금 승인
```

입력값:

```text
현금영수증 휴대폰 번호: 01000000000
은행: 기업은행
계좌번호: 34108755301018
```

### 7.12 계약 요청 취소

흐름:

```text
앱 재실행
-> 홈 화면 풀 리프레시
-> 계약 요청 상태 카드 선택
-> 계약 상세 진입
-> 최하단 계약 취소
-> 기타 제외 취소 사유 랜덤 선택
-> 계약 취소 버튼 활성화 확인
-> 계약 취소
```

PASS 기준:

- 계약 요청 취소 완료 상태 또는 홈 복귀 상태가 확인되어야 한다.

### 7.13 계약 확정 취소

흐름:

```text
앱 재실행
-> 홈 화면 풀 리프레시
-> 예약 확정 카드 선택
-> 계약 상세 진입
-> 최하단 계약 취소
-> 계약을 취소하시겠어요? 팝업에서 계약 취소
-> 호스트 전달 취소 사유 선택
-> 다음
-> 무통장 입금 계약이면 환불 받으실 계좌정보 확인 화면에서 다음
-> 취소 내역 확인 화면 하단 이동
-> 위 내용을 모두 확인하였습니다 선택
-> 취소하기
-> 취소가 완료되었습니다! 팝업 확인
-> 리브애니웨어 취소 사유 전달 화면 닫기
-> 홈 화면 확인
```

PASS 기준:

- 최종 취소 완료 팝업을 확인해야 한다.
- 리브애니웨어 취소 사유 전달 화면을 닫고 홈 화면까지 복귀해야 한다.

## 12. 현재 리스크와 대응

### 12.1 UI 변경 리스크

문제:

- 앱 UI 문구, 버튼 위치, 화면 구조가 바뀌면 자동화가 실패할 수 있다.

대응:

- 좌표보다 UI dump 기반 탐색을 우선 사용한다.
- 실패 시 XML과 스크린샷을 저장한다.
- 버튼 텍스트 변경 시 탐색 조건을 업데이트한다.

### 12.2 XML 노드 분리 문제

문제:

- 일부 React Native 팝업은 화면에는 버튼이 보이지만 Android XML에서는 팝업 전체 텍스트 하나로만 잡힌다.

대응:

- 특정 팝업 문구가 확인된 경우에만 제한적으로 좌표 fallback을 사용한다.
- 무분별한 좌표 탭은 금지한다.

### 12.3 입력기와 키패드 문제

문제:

- 카드번호, 계좌번호 입력 후 키패드가 버튼을 가릴 수 있다.

대응:

- 입력 후 키패드 내리기 또는 적절한 스크롤을 수행한다.
- 버튼이 실제로 활성화되었는지 확인한 뒤 탭한다.

### 12.4 잘못된 PASS 판정 리스크

문제:

- 버튼을 눌렀지만 실제 상태가 바뀌지 않았는데 성공으로 오판할 수 있다.

대응:

- 각 테스트의 최종 화면을 반드시 확인한다.
- 오류 문구가 보이면 FAIL 또는 부가 이슈로 기록한다.
- 로그인/결제/취소는 완료 화면 또는 홈 복귀까지 확인한다.

### 12.5 연결 실행 중복 처리 리스크

문제:

- 계약 요청 PASS 후 자동 승인, 기본검증 내부 승인, 수동 승인 명령이 섞이면 같은 계약을 중복 처리할 수 있다.

대응:

- 기본검증 내부에서는 개별 명령의 자동 연결을 우회하고 단계별 테스트를 직접 호출한다.
- 호스트 승인은 기본검증 플로우 안에서 한 번만 실행한다.
- 무통장 입금 승인은 무통장 결제 PASS 이후에만 실행한다.

## 15. 요약

`qa-bot-v2`는 Slack 명령어로 LiveAnywhere Android 앱의 핵심 게스트/호스트 시나리오를 실행하는 QA 자동화 봇이다.

앞으로는 TargetSdk 36 화면 진단, 리뷰/쿠폰/알림/채팅 등 주변 시나리오, iOS/Web 자동화로 확장한다.
